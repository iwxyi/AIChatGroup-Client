# Pneumata Client

> 不是把 AI 放进聊天框。  
> 是让一群角色带着关系、记忆、情绪和旧经历，进入同一个房间继续生活。

Pneumata Client 是 Sense Murmur 的前端应用：一个面向 **多角色群聊、长期角色关系、互动房间、AI Agent 与模型中转** 的本地优先客户端。

它的核心不是“多几个聊天模式”，而是一套能够承载角色连续性的互动平台：角色会记住你，也会记住彼此；关系会改变发言、站队、沉默和护短；故事、讨论、陪伴、任务和社交动态都可以接在同一个运行底座上。

## 一句话定位

**Pneumata 是一个 AI 多角色互动房间客户端，用房间内核、事件流、关系记忆和可见性系统，把“角色聊天”推进到可持续演化的角色世界。**

它既是产品，也是实验场：

| 维度 | 它解决什么 |
|---|---|
| 多角色群聊 | 多个 AI 角色围绕同一话题自然接话、插话、沉默、拆台、补台 |
| 角色连续性 | 同一角色跨群聊、单聊、故事和任务保持人格、关系和记忆一致 |
| 长期关系 | 角色对用户、对其他角色、对房间形成可持续变化的关系 |
| 互动房间 | 聊天只是表面，底层可以承载故事、讨论、教学、任务和规则玩法 |
| Agent 产物 | 普通聊天之外，可把任务推进为文档、代码、图表、网页程序等产物 |
| AI 中转站 | 统一管理模型接入、Key、额度、转发与使用边界 |

## 它和普通 AI 聊天有什么不同

普通 AI 聊天的核心是“一次输入，一次输出”。Pneumata 的核心是“一个房间里发生了什么，以及这些事情如何改变角色”。

| 普通 AI 聊天 | Pneumata |
|---|---|
| 一个助手回答用户 | 多个角色在同一房间中相互影响 |
| 会话结束后体验重置 | 关系、记忆、陪伴状态会持续沉淀 |
| 角色主要靠 prompt 扮演 | 角色由设定、关系、记忆、情绪和场景共同驱动 |
| 聊天记录是主要资产 | 用户与角色共同经历才是主要资产 |
| 多功能靠入口堆叠 | 多玩法共享房间内核、事件流和投影系统 |
| Agent 是另一个孤立工具 | Agent 是房间能力的一部分，产物可保存、可修改、可回看 |

真正的差异不在“能不能聊天”，而在：

- 角色会因为过去的事情改变今天的语气。
- 群聊里不是所有人都抢着回答，而是谁该接、谁该让、谁该沉默。
- 单聊里的亲密、群聊里的站队、故事里的选择、任务里的协作，可以共享同一段关系历史。
- 模板只是角色的起点；真正不可复制的是用户和角色共同养出来的实例。

## 核心功能

### 多角色群聊

多角色群聊是 Pneumata 的第一主线。它不是“随机挑一个角色回复”，也不是“让所有角色轮流表演”。

系统会根据当前话题、用户指向、角色关系、最近记忆和房间气氛，判断谁更应该回应、谁应该补充、谁适合拆台、谁可以保持沉默。

你会看到：

| 能力 | 用户感知 |
|---|---|
| 多角色同场 | 角色之间会接话、反驳、缓和、围观、开玩笑 |
| 发言选择 | 不是每轮所有人都说，而是更像真实群聊的节奏 |
| 关系影响 | 关系好的角色可能护短，关系差的角色可能质疑或拆台 |
| 旧事回到当下 | 角色会把以前发生过的事带回当前语境 |
| 场景内连续性 | 一个房间聊久后，会形成共同梗、房间气氛和群体结构 |

### 角色多维设定

角色不是一句人设，也不是单个 system prompt。

Pneumata 里的角色由多层信息共同塑造：

| 层 | 说明 |
|---|---|
| 基础设定 | 名字、外观、人格、说话方式、擅长领域 |
| 表达风格 | 语气、长度、节奏、情绪强度、克制度 |
| 关系状态 | 对用户、对其他角色、对房间的亲近、信任、防备和威胁感 |
| 记忆状态 | 经历过什么、记住了什么、哪些事改变了她 |
| 陪伴状态 | 称呼、仪式、共同话语、主动关怀和边界 |
| 场景状态 | 当前房间里的身份、目标、阶段、线索、任务或局势 |

这让同一个模板角色在不同用户那里逐渐长成不同的角色实例。

### 长期记忆与关系

Pneumata 不把记忆理解成“聊天摘要仓库”。更重要的是角色经历过什么、如何理解那件事、留下了什么后效。

| 能力 | 说明 |
|---|---|
| 关系变化 | 亲近、信任、威胁、防备、依赖、竞争会影响后续行为 |
| 记忆分层 | 角色核心记忆、关系记忆、房间记忆、场景记忆和事件记忆分开沉淀 |
| 行为后效 | 一次被忽视、一次被维护、一次争执或一次共同完成，会改变角色之后的反应 |
| 跨房间延续 | 角色进入新房间时不会完全重置，会带着旧关系和旧经历 |
| 可控写入 | 重要事实优先来自结构化输出、用户保存或事件回放，避免本地关键词误判污染记忆 |

### 亲密陪伴

亲密陪伴不是单聊皮肤，而是关系和记忆之上的高权重投影。

它可以体现在：

| 维度 | 例子 |
|---|---|
| 称呼 | 私下称呼、公开称呼、关系变化后的称呼变化 |
| 仪式 | 早安、晚安、纪念日、和好后的固定表达 |
| 共同话语 | 只有用户和角色之间才懂的一句话 |
| 主动关怀 | 在边界、冷却和节律控制下的低频关注 |
| 跨场景影响 | 虚拟伴侣进入群聊、故事或讨论时，仍然带着与你的关系 |

### 互动房间与玩法

Pneumata 的设计不是“每个玩法做一套孤岛”，而是把玩法看成房间能力的不同组合。

| 房间方向 | 可以承载什么 |
|---|---|
| 自由群聊 | 日常陪伴、群像互动、吐槽、争论、关系事件 |
| 故事房 | 分支剧情、章节推进、角色立场、旧关系进入新剧情 |
| 讨论 / 审议 | 多角色立场、攻防、质询、总结、裁决 |
| 教学 / 训练 | 长期学习目标、弱点追踪、陪学反馈、阶段练习 |
| 剧本杀 / 狼人杀 | 身份、线索、投票、私有视角、背刺和掩护 |
| 创作工坊 | 人设、剧情、世界观、方案、版本和产物沉淀 |
| Agent 房 | 目标、计划、分工、执行状态和结果产物 |

当前最优先打磨的是 **自由群聊** 和 **故事房**，因为它们最能体现角色连续性、关系后效和多角色互动的价值。

### 朋友圈与活动日历

动态和日历不是独立社交 App，而是角色世界的回声层。

| 模块 | 作用 |
|---|---|
| 朋友圈 / 动态 | 让角色互动、状态变化、日常片段形成可回看的世界痕迹 |
| 活动日历 | 承接邀约、约定、纪念日、行程和共享活动 |
| 世界事件 | 把聊天里真正成立的事件投影到后续关系、记忆和提醒中 |

关键点：系统不会用简单关键词从聊天文本硬抽日历或关系事实。重要事件需要来自 AI 结构化结果、用户确认或已有事件回放，优先保证长期状态不被误写污染。

### Agent 工作流

Pneumata 的 Agent 不是主线，但它是平台能力的重要延展。

当用户需要把对话推进为结果时，Agent 可以承接：

| 产物 | 示例 |
|---|---|
| 文档 | 方案、报告、总结、教程、产品说明 |
| 代码 | 代码片段、多文件文本工程、HTML 小工具 |
| 图表 | Mermaid、流程图、结构图、数据表 |
| 网页程序 | 可预览的 HTML/CSS/JS 小应用 |
| 文件内容 | JSON、CSV、TSV、多文件文本源 |

Agent 的重点不是“回复看起来很强”，而是产物可保存、可版本化、可修改、可预览、可下载，并且不拖慢普通聊天体验。

### AI 中转站

AI 中转站面向有模型使用需求的用户和开发者。

| 能力 | 说明 |
|---|---|
| 多模型接入 | 管理不同模型供应商和调用方式 |
| Key 管理 | 统一管理凭据、额度和使用边界 |
| API 转发 | 对外提供兼容式转发入口 |
| 权益控制 | 与会员、用户配置和平台权限联动 |
| 体验统一 | 前端体验不被底层模型差异割裂 |

## 技术架构思想

这里不展开源码，但 Pneumata 的技术难点并不在“调一个大模型接口”。真正的挑战是：如何让多个角色、多个房间、多个玩法、多个可见性视角，在长期运行后仍然保持一致。

### 1. Room Kernel：房间是主实体

聊天只是房间的一种表面。房间才是承载规则、参与者、阶段、事件、视角和产物的核心实体。

| 层 | 负责什么 |
|---|---|
| 房间内核 | 房间类型、玩法规则、阶段、参与结构 |
| 交互表面 | 文本、表单、棋盘、时间轴、仪表盘、混合界面 |
| 频道结构 | 公共频道、用户私域、角色私聊、主持视角、裁判视角 |
| 运行状态 | 当前话题、阶段、线索、任务、目标、棋局或剧情节点 |

这意味着一个新玩法不需要从零发明一套聊天系统，而是接入同一套房间运行底座。

### 2. Event-first Runtime：事件是事实源

Pneumata 把消息、动作、阶段变化、关系变化、记忆候选、日历活动、投票、线索、产物等都视为运行事件。

这样做的价值是：

| 能力 | 价值 |
|---|---|
| 可追溯 | 能知道一次关系变化、记忆写入或活动创建来自哪里 |
| 可投影 | 同一份事实可以投影成用户视图、角色视图、开发者视图 |
| 可回放 | 房间状态不是散落 UI 状态，而能从事件链理解 |
| 可治理 | 私密事件、公开摘要、结构化写入有明确边界 |

这也是长期角色系统的基础：没有统一事实源，长期记忆和关系最终会变成不可调试的 prompt 黑箱。

### 3. Soul Runtime：角色连续性的运行层

角色连续性不是一句“请保持人设”能解决的。

Pneumata 将角色表现拆成多层：

```txt
房间消息 / 用户动作 / 世界事件
-> 结构化事件
-> 关系变化 + 分层记忆 + 情绪后效
-> 角色当前状态
-> 本轮行为倾向
-> 表达计划
-> 消息 / 动作 / 产物
```

这套机制让角色的“像自己”不是静态人设，而是长期经历在当前场景中的投影。

### 4. 多角色发言不是轮询

多角色群聊最容易做成两种廉价版本：

- 所有人轮流说一句。
- 随机选一个人回答。

Pneumata 的目标是更接近真实群聊：

| 判断维度 | 影响 |
|---|---|
| 用户是否点名 | 明确对象优先回应 |
| 当前话题压力 | 决定该接话、追问、降温还是转移 |
| 角色关系 | 影响护短、拆台、沉默、支持和回避 |
| 最近发言节奏 | 避免单个角色霸屏，也避免机械平均 |
| 记忆相关性 | 相关旧事会影响谁更该出声 |
| 场景规则 | 故事、讨论、任务、游戏房都有不同发言边界 |

用户看到的是一条自然消息，背后是一整套选择与表达判断。

### 5. Projection：不同视角看到不同世界

Pneumata 支持公共群聊、用户单聊、角色之间私密线程、主持视角、玩法私密信息和公开摘要回流。

这要求系统区分：

| 视角 | 例子 |
|---|---|
| 公共可见 | 群聊消息、公开事件、阶段变化 |
| 用户私域 | 用户与角色的单聊、亲密陪伴、个人反馈 |
| 角色私密 | 角色之间的私聊、局内秘密、阵营信息 |
| 主持 / 裁判 | 剧本杀、狼人杀、教学或面试中的控制信息 |
| 公开摘要 | 私密事件对公共世界造成的结果，而不是泄露原文 |

这让“角色世界”可以有层次，而不是把所有信息都塞进同一个聊天框。

### 6. Capability Graph：玩法能力组合

Pneumata 不希望每个玩法都变成一套硬编码分支。更理想的方式是把房间类型、玩法规则、角色设定、表达风格、频道语义和用户设置汇总为当前可用能力。

| 能力类别 | 示例 |
|---|---|
| 回复能力 | 回谁、是否允许多人接话、是否允许短回复 |
| 社交能力 | 安抚、拆台、护短、修复、调侃 |
| 结构能力 | 是否需要 Markdown、总结、表格、长文 |
| 玩法能力 | 投票、搜证、分支选择、局内行动 |
| 媒体能力 | 图片、音频、附件、富消息 |
| 校验能力 | 去重、用户明确要求命中、结构化结果校验 |

对开发者而言，这代表玩法扩展不是“继续堆 prompt”，而是让规则、能力和表达层分离。

## 工程特点

### 本地优先

Pneumata Client 重视本地可用性和用户资产控制。

| 能力 | 说明 |
|---|---|
| 本地数据 | 角色、房间、消息、设置、产物等优先在本地维护体验闭环 |
| PWA | 支持 Web App 形态和离线资产缓存 |
| 渐进云同步 | 云端同步围绕身份、范围、冲突和权益逐步开启 |
| 产物边界 | 大型产物、导出文件、工程包不默认进入官方云同步 |

### 可调试运行时

长期 AI 系统最怕“看起来对，但不知道为什么”。Pneumata 的设计强调运行痕迹：

| 调试对象 | 可以解释什么 |
|---|---|
| 发言选择 | 为什么是这个角色回应，为什么其他角色沉默 |
| 生成计划 | 本轮表达目标、情绪姿态和回应表面 |
| 结构化写入 | 哪些关系、记忆、活动或事件被接受 / 拒绝 |
| 可见性裁剪 | 为什么某些信息只在特定视角出现 |
| Agent 产物 | 产物如何创建、如何修改、版本如何变化 |

这不是为了给普通用户看复杂度，而是为了让系统能被维护、被验证、被继续扩展。

### 隐私和边界

角色长期记忆很有吸引力，也很危险。Pneumata 的设计原则是：

- 私密内容不直接泄露到公共房间。
- 关系、记忆、日历等长期事实不靠本地关键词硬猜。
- 公开回流只回流摘要、结果或行为后效，不回流私密原文。
- 用户资产、模型 Key、产物正文和同步范围必须有清晰边界。

### 现代前端体验

客户端基于 React、TypeScript、Vite、MUI、Zustand、Vitest 等现代前端栈构建，重点不是炫技，而是支撑复杂互动产品：

| 能力 | 作用 |
|---|---|
| 响应式布局 | 适配桌面、移动端、侧栏、产物面板等多种密度 |
| 富消息渲染 | Markdown、代码、媒体、图表、文件卡、系统事件 |
| 虚拟列表 | 支撑长消息流和复杂聊天记录 |
| 主题系统 | 支持亮色、暗色、品牌外观和产品介绍页的动态适配 |
| 测试与构建 | 使用 TypeScript、ESLint、Vitest 和 Vite build 保持基础质量 |

## 典型体验

### 1. 建一个多角色群聊

创建几个角色，把他们放进同一个话题。你不需要安排每个人说什么，系统会根据场面和角色状态判断谁该回应。

结果不是“多人客服”，而是更像一群有关系的人在聊天。

### 2. 养一个会变化的角色

一个角色初始可能只是模板，但随着你们经历争执、安慰、合作、冷场、约定和共同完成，她会逐渐形成只属于你的关系历史。

同一个模板，在不同用户那里应该长成不同的人。

### 3. 把旧关系带进新房间

你可以把同一批角色带进故事房、讨论房、教学房或任务房。

关键不是换了新玩法，而是角色不会丢掉过去。她在新房间里的站队、语气、主动性和沉默，都可能带着旧关系的影子。

### 4. 让 Agent 接住任务

当聊天里出现真正的任务需求，Agent 可以把它推进成文档、代码、图表、网页程序或文件内容。

普通聊天保持轻，任务能力按需打开。

## 最后一层差异

Pneumata 想证明一件事：

**AI 角色产品的壁垒，不是更会说漂亮话，而是能不能让角色在长期关系、不同场景和复杂事件后，仍然像同一个人。**

如果一个角色会记得你、会被你改变、会在群聊里偏袒或回避、会把旧关系带进故事和任务里，那么它就不再只是一次回答。

它开始拥有历史。
